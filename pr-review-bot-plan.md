# План реалізації: агентний PR Review бот

> Документ-завдання для виконавця (Claude Code). Описує **що** і **в якому порядку** будувати. Конкретні рішення з реалізації (мова, фреймворк воркера, хостинг) лишаю на виконавця там, де це не критично; де критично — позначено явно.

## 1. Огляд та мета

Побудувати бота, який автоматично рев'юить Pull Request-и в GitHub. На кожен новий/оновлений PR бот:

1. визначає, що змінилось і що ці зміни можуть зачепити (детерміновано, без LLM);
2. передає ці факти в LLM, який формує два артефакти — менторський фідбек для junior-розробника та стисле summary для senior-рев'ювера;
3. постить результат назад у PR як коментарі.

### Ключова архітектурна ідея — два шари

- **Детермінований шар.** Звичайний код, нуль LLM. Відповідає на механічні питання: які файли/функції змінились, хто від них залежить (blast radius), де бракує тестів, наскільки ризиковано. Цей шар **повністю закриває стороння бібліотека `code-review-graph`** — її не треба переписувати, лише викликати як CLI і парсити JSON-вивід.
- **LLM-шар.** Викликається рівно один раз за PR. Бере готові факти від детермінованого шару + сам diff і перетворює їх на людський фідбек. LLM **не шукає проблеми сам і не сканує репозиторій** — він інтерпретує вже зібрані факти.

### Це пайплайн, а не агент

Послідовність кроків фіксована й відома наперед (подія → код → граф → JSON → LLM → коментарі). Тому:

- **НЕ використовувати** LangChain / агентні фреймворки. Зайва абстракція для фіксованого конвеєра.
- Для виклику LLM використати **офіційний SDK провайдера** (напр. `anthropic` або `openai`).
- `code-review-graph` повністю замінює потребу у власному retrieval / векторних базах — пошук релевантного коду робить він.

## 2. Сторонні залежності — вивчити ПЕРЕД кодуванням

> Виконавцю: спочатку прочитати ці джерела, бо від них залежать формати даних і команди.

- **`code-review-graph`** (PyPI / GitHub `tirth8205/code-review-graph`). Парсить кодову базу через Tree-sitter, будує граф (вузли: функції, класи, імпорти; ребра: виклики, наслідування, тести) у локальному SQLite-файлі в теці `.code-review-graph/`. Потрібен Python 3.10+ та `uv`.
  - Перед використанням: запустити `--help` для команд `build`, `update`, `detect-changes` і **зафіксувати реальний формат JSON-виводу `detect-changes`** (структура може відрізнятись від описаної тут — орієнтуватись на фактичний вивід версії, що встановлена).
  - Розглянути форк `n24q02m/better-code-review-graph` як альтернативу (має додаткові примітиви для витягання фрагментів коду зачеплених сусідів). Вибір зафіксувати на старті.
- **GitHub API / GitHub App** — REST API для отримання diff, постингу review-коментарів; механіка webhook-ів та installation access token.
- **LLM SDK** — офіційний SDK обраного провайдера.

## 3. Компоненти системи

```
[GitHub] --webhook--> [Web-сервер] --enqueue--> [Черга] --> [Воркер]
                           |                                    |
                       verify + 200 OK                          v
                                                    clone -> graph -> LLM -> post
```

- **Web-сервер** — приймає webhook, верифікує, ставить завдання в чергу, миттєво відповідає `200 OK`.
- **Черга + воркер** — асинхронна обробка (напр. Celery/RQ або аналог). Воркер виконує важку роботу.
- **Обгортка над `code-review-graph`** — модуль, що запускає CLI-команди й парсить вивід.
- **LLM-модуль** — формує запит, викликає API, розбирає відповідь на два артефакти.
- **GitHub-клієнт** — токени, отримання diff, постинг коментарів.

## 4. Покроковий конвеєр (порядок реалізації)

### Крок 1 — GitHub App та приймання webhook

- Зареєструвати GitHub App; підписка на події `pull_request` (`opened`, `synchronize`, `reopened`).
- Web-ендпоінт для webhook:
  - **верифікувати HMAC-підпис** webhook (секрет App-а) — відкидати невалідні;
  - дістати з payload: `repository`, `base` SHA, `head` SHA, номер PR, `installation_id`;
  - покласти завдання в чергу й **одразу повернути `200 OK`** (не блокувати GitHub обробкою).
- **Критично:** вся важка робота — у воркері, не в обробнику webhook. GitHub повторно шле подію при таймауті.

### Крок 2 — Отримання коду (воркер)

- Отримати короткоживучий **installation access token** через credentials App-а.
- `git clone` репозиторію в тимчасову робочу теку.
- **Критично:** забезпечити, щоб в історії були присутні і `base`, і `head` SHA (інакше `detect-changes --base` не спрацює). Не покладатись на надмірно shallow checkout. Для першого аналізу — повний clone.

### Крок 3 — Побудова графа

- Без кешування (за умовою задачі): **щоразу `build` з нуля**.
  - `code-review-graph build` — парсинг усієї кодової бази (~10с на 500 файлів).
- Для дуже великих репо передбачити запобіжники від зависання через env-змінні бібліотеки: `CRG_MAX_CHANGED_FUNCS`, `CRG_MAX_TRANSITIVE_FRONTIER`, `CRG_TOOL_TIMEOUT` (перевірити актуальні назви в `--help`/доках). Обробляти timeout-помилку як нефатальну (деградувати до рев'ю по самому diff).

> Примітка: кешування графа між запусками свідомо пропущено. Архітектуру лишити так, щоб кеш можна було додати пізніше окремим шаром (винести роботу з графом в окремий модуль із чітким інтерфейсом `ensure_graph(repo, base, head)`).

### Крок 4 — Аналіз змін (детермінований шар)

- Запустити `code-review-graph detect-changes --base <base_sha>` (повний JSON-вивід, **без** `--brief`).
- Розпарсити JSON у внутрішню структуру. Очікувані поля (звірити з реальним виводом): перелік змінених файлів/функцій, blast radius (хто зачеплений), прогалини в тестовому покритті, ланцюги залежностей, risk score.
- Окремо отримати **сам diff** PR через GitHub API (потрібен LLM для прив'язки коментарів до рядків).
- Результат кроку — «пакет фактів»: `{ structured_facts_from_graph, raw_diff }`.

### Крок 5 — LLM-інтерпретація (один виклик)

- Сформувати запит до LLM:
  - **system prompt** — роль досвідченого, конструктивного код-рев'ювера;
  - **контекст** — пакет фактів з кроку 4 (JSON графа + diff);
  - **інструкція** — згенерувати ДВА артефакти за один прохід:
    - *junior*: менторський фідбек, прив'язаний до конкретних рядків diff — що не так, **чому**, що може зламатись (брати з blast radius), як виправити;
    - *senior*: стисле summary — risk score, зачеплені flow, прогалини в тестах, на що звернути увагу.
  - Промпт-патерн: «ось факти — **поясни і пріоритизуй**», НЕ «знайди проблеми». Факти вже зібрані детерміновано; завдання LLM — інтерпретація, не пошук.
- Попросити LLM повернути **структуровану відповідь** (напр. JSON з полями `junior_comments[]` із прив'язкою до файл+рядок, та `senior_summary`), щоб її було легко розібрати для постингу. Безпечно парсити (обробити випадок невалідного JSON).

### Крок 6 — Публікація в PR

- Через GitHub Review API:
  - `junior` фідбек → **inline review comments** на конкретні рядки diff;
  - `senior` summary → **тіло review** (загальний коментар).
- **Ідемпотентність:** при `synchronize` (новий пуш у той самий PR) не плодити дублі — або оновлювати попередній review, або згортати/позначати застарілі коментарі. Зберігати мінімальний маппінг `PR → останній оброблений head SHA`.

### Крок 7 — Прибирання

- Видалити тимчасову робочу теку (clone + згенерований SQLite-граф).
- Звільнити/не логувати токени.

## 5. Обробка помилок та крайові випадки

- **Force-push / зміна історії:** якщо `base` SHA недоступний у клоні — робити повний `build` і аналіз по доступному diff. Не падати.
- **Непідтримувана мова:** `code-review-graph` покриває багато мов, але не всі. Якщо граф не дав корисних фактів — **деградувати**: робити рев'ю по самому diff без blast radius (LLM-шар має вміти працювати і без графових фактів).
- **LLM повернув невалідний формат:** ретрай або fallback на постинг лише summary.
- **Великі PR / таймаути графа:** застосувати env-ліміти (Крок 3), деградувати.
- **GitHub rate limits:** ретраї з backoff на постингу.
- Усі помилки логувати; завдання в черзі — з обмеженим retry.

## 6. Конфігурація (env / secrets)

- GitHub App: `APP_ID`, приватний ключ, `WEBHOOK_SECRET`.
- LLM: `API_KEY`, назва моделі.
- Ліміти `code-review-graph` (назви звірити з докою).
- Налаштування черги/брокера.

## 7. Порядок робіт для виконавця (мілстоуни)

1. **Каркас сервісу:** web-ендпоінт webhook з верифікацією підпису + чергою + порожнім воркером (логує подію). Перевірити, що GitHub доходить до воркера.
2. **GitHub-клієнт:** токени, clone репо, отримання diff, постинг тестового коментаря в PR. End-to-end «touch» PR-а.
3. **Обгортка `code-review-graph`:** модуль `ensure_graph()` + `detect_changes()`, що повертає розпарсені факти. Покрити реальним виводом CLI.
4. **LLM-модуль:** виклик SDK, промпт, розбір відповіді на два артефакти. Тестувати на збережених прикладах фактів.
5. **Збірка конвеєра:** з'єднати кроки 1–6 у воркері.
6. **Крайові випадки та деградація** (розділ 5).
7. **Ідемпотентність** на `synchronize`.

> На кожному мілстоуні — мінімальні тести. Спершу наскрізний «тонкий» прохід (хай навіть із заглушкою LLM), потім нарощувати якість.

## 8. Свідомо поза рамками (не реалізовувати зараз)

- Кешування графа між запусками (винести інтерфейс так, щоб додати пізніше).
- Справжня агентна поведінка (цикл «думка → інструмент → результат»). Поточна версія — фіксований пайплайн.
- MCP-інтеграція з `code-review-graph` — використовуємо CLI напряму, MCP не потрібен.
- Підтримка не-GitHub платформ.
